# Lesson 1 — Setting Up the Development Environment

## Objective

Create an isolated Python development environment for Project Cardinal and establish the connection between Python, Ollama, and the locally installed Gemma model.

## Development Environment

- Operating System: Windows
- Programming Language: Python 3.11
- Development Environment: Visual Studio Code
- Local LLM Runtime: Ollama
- Initial Language Model: Gemma 3 4B
- Python environment: `venv`

## Virtual Environments

A Python virtual environment provides an isolated Python environment for a project.

Instead of installing packages globally on the computer, dependencies required by Project Cardinal are installed inside `.venv`.

This helps prevent conflicts between different Python projects.

The environment was created with:

```bash
python -m venv .venv
```

An important practical lesson was that VS Code must use the Python interpreter belonging to this virtual environment.

## Issue Encountered: PowerShell Script Execution

Windows PowerShell initially prevented execution of the virtual-environment activation script because of its execution policy.

Possible solutions included using Command Prompt or adjusting the PowerShell execution policy.

## Key Learning

A Python project is not defined only by its source code. The Python interpreter, environment, installed dependencies, and configuration are also part of the development environment.

# Lesson 2 — Communicating with a Local LLM

## Objective

Send a prompt from Python to Gemma running locally through Ollama.

The fundamental interaction was:

```python
from ollama import chat

response = chat(
    model="gemma3:4b",
    messages=[
        {
            "role": "user",
            "content": "Explain Newton's First Law."
        }
    ]
)

print(response["message"]["content"])
```

## Architecture

The basic request flow is:

```text
Python Application
       │
       ▼
Ollama
       │
       ▼
Gemma 3 4B
       │
       ▼
Generated Response
```

Ollama acts as the runtime that allows the Python application to communicate with the locally installed language model.

## Chat Messages

LLMs receive conversations represented as messages.

Important roles include:

```text
system
user
assistant
```

The `system` message provides instructions governing the model's behaviour.

The `user` message contains the user's input.

The `assistant` messages represent previous responses generated by the model.

## Key Learning

The language model is only one component of an AI application. Python controls what information is sent to the model and what happens with the resulting response.

# Lesson 3 — Conversation Memory

## Objective

Turn a single question-and-answer interaction into a multi-turn conversation.

## Core Concept: LLMs Are Stateless

Gemma does not inherently remember previous API calls.

Conversation memory was implemented by maintaining a Python list:

```python
messages = []
```

Every user message and assistant response is appended to this list.

The entire relevant conversation is then sent back to Gemma on subsequent calls.

Conceptually:

```text
System
User Question 1
Assistant Answer 1
User Question 2
Assistant Answer 2
...
```

The model appears to remember because the application provides the previous conversation again.

## Important Distinction

Conversation memory belongs primarily to the **application**, not to the LLM.

This distinction will later become important when implementing persistent memory and RAG.

## Issue Encountered: Incorrect Python Environment

The application initially produced:

```text
No module named 'ollama'
```

The problem was that VS Code was using a different Python interpreter from the project's virtual environment.

This was diagnosed using commands such as:

```bash
python --version
python -m pip show ollama
python -c "import sys; print(sys.executable)"
```

## Key Learning

When Python reports that an installed package cannot be found, verify which Python interpreter is actually executing the program.

# Lesson 4 — Object-Oriented Tutor Design

## Objective

Move from a function-based chatbot toward an extensible application architecture.

A `Tutor` class was introduced.

Conceptually:

```python
class Tutor:

    def __init__(self):
        self.messages = []

    def ask(self, question):
        ...
```

## Why Use a Class?

A Tutor object can maintain its own state.

Instead of one global conversation:

```text
Application
    │
    └── messages
```

we can have:

```text
Application
    │
    ├── Tutor A
    │      └── conversation
    │
    └── Tutor B
           └── conversation
```

This creates the possibility of different tutors, students, subjects, and sessions later.

## Understanding `self`

`self` refers to the particular instance of a class.

For example:

```python
tutor = Tutor()
```

When calling:

```python
tutor.ask(question)
```

Python automatically supplies `tutor` as the `self` argument.

## Issue Encountered: Calling Instance Methods

An error occurred when the method was effectively being called on the class rather than the Tutor instance.

The correct pattern is:

```python
tutor = Tutor()
tutor.ask(question)
```

rather than calling `Tutor.ask()` directly without an instance.

## Issue Encountered: `__init__`

Another error occurred because the constructor was typed with incorrect underscores.

Python requires:

```python
__init__
```

with two underscores before and after `init`.

Because the incorrectly named method was never called as the constructor, attributes such as:

```python
self.messages
```

were never created.

This resulted in:

```text
Tutor object has no attribute 'messages'
```

## Key Learning

Python's special methods such as `__init__` have exact names. Small syntax differences can fundamentally change program behaviour.

# Lesson 6 — Conversation, Memory and Knowledge

## Objective

Establish a clear distinction between three fundamental concepts.

## Conversation History

Conversation history represents the current dialogue.

Example:

```text
Student: I don't understand equilibrium.
Tutor: Which part is confusing?
Student: I don't understand why...
```

It primarily provides short-term conversational context.

## Student Memory

Student memory represents information about the learner.

Examples:

```text
Struggles with chemical equilibrium
Strong in differentiation
Prefers visual explanations
Often makes sign errors
```

This information should survive individual conversations.

## Knowledge Base

The knowledge base contains information the tutor can teach from.

Examples:

- NCERT textbooks
- School notes
- Reference material
- Question papers
- Formula sheets

This is where Retrieval-Augmented Generation will eventually operate.

## Mental Model

A human tutor similarly has three different things:

```text
Knowledge of the subject

Knowledge of the student

Memory of today's lesson
```

Project Cardinal should maintain the same separation.

## Conversation Management

Additional Tutor methods were introduced, including:

```python
clear_conversation()
conversation_length()
```

These demonstrated the principle that methods should have focused responsibilities.

## Key Learning

Memory and knowledge are not the same thing.

RAG provides relevant **knowledge**.

Student memory provides relevant **personal context**.

Conversation history provides relevant **immediate context**.

Database identity should be managed by the database rather than manually calculated by the application.

## Lesson 10A — Primary Keys, Foreign Keys and Relational Design

The database was redesigned from a simple student-profile table toward a
relational learning model.

### Primary Keys

A primary key uniquely identifies a record within a table.

For example:

    students
    --------
    id
    name

The `id` column is the primary key.

### Foreign Keys

A foreign key connects a record to a record in another table.

For example:

    student_subjects.student_id
                  ↓
             students.id

and:

    student_subjects.subject_id
                  ↓
             subjects.id

Foreign keys allow the database to maintain referential integrity.

### Relational Model

The initial learning model consists of:

    students
        │
        ├── student_subjects ── subjects
        │                           │
        │                           ▼
        │                         topics
        │
        └── student_topics ────────┘

### Tables

students

    id
    name
    grade
    board
    learning_style

subjects

    id
    name

student_subjects

    student_id
    subject_id

topics

    id
    subject_id
    name

student_topics

    student_id
    topic_id
    status
    confidence
    last_revised

### Important Design Principle

Information about a subject or topic should be separated from information
about the student's relationship with that subject or topic.

For example:

"Integration" is a property of the topic.

"The student is weak at Integration" is a property of the relationship
between the student and the topic.

Therefore, the latter belongs in `student_topics`.

### Composite Keys

`student_subjects` and `student_topics` use a combination of IDs as their
primary key.

For example:

    PRIMARY KEY (student_id, subject_id)

This prevents the same subject from being assigned to the same student
more than once.

### SQLite Foreign Keys

SQLite foreign-key enforcement was explicitly enabled using:

    PRAGMA foreign_keys = ON

This allows SQLite to enforce relationships between the tables.

### Design Decision

The database is being designed with reasonable relational structure even
though the initial application has only one student.

We will not implement multi-user functionality unless it becomes necessary.

## Lesson 10B — Subjects and Topics

Project Cardinal's database was extended to represent the relationship between

### Relationships

A student can study multiple subjects.

A subject can contain multiple topics.

A student can have a different learning state for each topic.

Therefore, topic-level attributes such as confidence, status and last revision
belong in `student_topics`, rather than in the `topics` table.

### Database operations added

- add_subject()
- get_subject()
- get_subjects()
- assign_subject()
- get_student_subjects()
- add_topic()
- get_subject_topics()

### Important Python lesson

A one-element tuple requires a trailing comma.

Correct:

(name,)

Incorrect:

(name)

Without the comma, `(name)` is simply the value itself. When the value is a
string, SQLite can interpret its individual characters as separate parameter
bindings, resulting in an error such as:

"Incorrect number of bindings supplied."

### Design principle

Master data and student-specific state should be separated.

For example:

"Integration" is a topic.

"The student is weak at Integration" is a property of the relationship
between the student and the topic.

This distinction will become important when we implement adaptive learning.

# Lesson 11 — Retrieval-Augmented Generation (RAG)

## Objective

Give Project Cardinal access to knowledge sources supplied by the user,
rather than relying entirely on the language model's built-in knowledge.

The initial implementation was deliberately kept simple so that each part
of the RAG process could be understood and tested independently.

---

## 11.1 — Loading Knowledge Sources

Created a `knowledge` folder for material that Cardinal will eventually use
as its trusted learning sources.

Example:

    knowledge/
        mathematics.txt

A simple document loader was created:

    def load_document(filename):
        with open(filename, "r", encoding="utf-8") as file:
            return file.read()

This established the first stage:

    Knowledge source
          ↓
    Load document
          ↓
        Text

The first test document contained basic information about integration.

---

## 11.2 — Chunking

Documents need to be divided into smaller pieces so that Cardinal can
retrieve relevant portions rather than passing an entire document to the
language model.

A simple character-based chunking function was implemented:

    def chunk_text(text, chunk_size=300):
        chunks = []

        for i in range(0, len(text), chunk_size):
            chunk = text[i:i + chunk_size]
            chunks.append(chunk)

        return chunks

This is intentionally a simple first implementation.

### Important learning

The current approach can split sentences or concepts in the middle.
This is acceptable for the first prototype.

Later, chunking can be improved using:

- paragraph boundaries
- sentence boundaries
- overlapping chunks
- document structure
- headings and sections

We deliberately deferred this optimization.

---

## 11.3 — Embedding Model

RAG needs a way to represent the meaning of text numerically.

A separate local embedding model was installed through Ollama:

    nomic-embed-text

The language model and embedding model have different responsibilities:

    phi4-mini
        ↓
    Generates/understands language

    nomic-embed-text
        ↓
    Converts text into numerical embeddings

Both models run locally through Ollama.

No cloud API is required.

---

## 11.4 — Generating Embeddings

The Python `ollama` package was already installed, so no additional
Python package was required.

An embedding was generated using:

    response = ollama.embed(
        model="nomic-embed-text",
        input=text
    )

The embedding was extracted using:

    embedding = response["embeddings"][0]

The result is a vector containing many numerical values representing
the semantic characteristics of the supplied text.

### Key learning

An embedding is not an answer.

It is a numerical representation that allows text to be compared
for semantic similarity.

---

## 11.5 — Similarity Search

A question was converted into an embedding and compared with the
embeddings of each document chunk.

Cosine similarity was used to measure similarity:

    cosine_similarity(vector_a, vector_b)

The process became:

    Student question
           ↓
       Embedding
           ↓
    Compare with chunks
           ↓
    Similarity scores
           ↓
    Rank chunks
           ↓
    Most relevant knowledge

The test successfully returned document chunks with similarity scores.

### Important learning

The similarity score is primarily useful for ranking results.
A particular numerical score should not automatically be interpreted
as "correct" or "incorrect".

---

## 11.6 — RAG + Phi-4

The highest-ranked chunks were supplied to the local language model:

    phi4-mini:latest

The resulting flow was:

    Question
        ↓
    Retrieve relevant chunks
        ↓
    Put chunks into prompt
        ↓
    phi4-mini
        ↓
    Answer

# 12A — Persistent Embedding Index

## Problem

The initial RAG implementation generated an embedding for every document
chunk every time a student asked a question.

This works for a small document but is inefficient for a larger knowledge
base.

## Solution

The document chunks and their embeddings were saved locally in a JSON
index.

The indexing process became:

    Knowledge document
          ↓
        chunks
          ↓
      embeddings
          ↓
    saved JSON index

The search process became:

    Student question
          ↓
    question embedding
          ↓
    compare against saved embeddings
          ↓
    ranked results

The embedding model used was:

    nomic-embed-text

The language model remains:

    phi4-mini:latest

No cloud service is required.

---

# 12B — Searching the Persistent Index

`rag_search.py` was modified so that it loads the saved embedding index
rather than generating document embeddings again.

The search process now:

1. Generates an embedding for the student's question.
2. Loads the previously generated document embeddings.
3. Calculates cosine similarity.
4. Sorts the results by similarity.
5. Returns the most relevant chunks.

This established a separation between:

## Indexing

    Document → chunks → embeddings → saved index

## Searching

    Question → embedding → similarity search → relevant chunks

This is a more scalable foundation for Cardinal's RAG system.

reasonable but often too verbose and repetitive.

- introduced unrelated analogies
- gave more explanation than was appropriate

The implementation was deliberately kept simple. We are not yet asking
the LLM to automatically determine mastery or change the student's
confidence.

---

# 15A — Updating Last Revised

A new method was added to `database.py`:

    update_topic_revision(
        student_id,
        topic_id,
        last_revised
    )

This method updates only the `last_revised` field in `student_topics`.

The existing:

    status
    confidence

values are left unchanged.

This keeps the database operation focused on one responsibility.

An indentation error was encountered while adding the method. The method
was initially placed incorrectly inside another method, causing:

    Database object has no attribute 'update_topic_revision'

The problem was corrected by placing the method at the same indentation
level as the other methods in the `Database` class.

This reinforced an important Python lesson:

> A method must be defined at the correct indentation level to belong to
> its intended class.

---

# 15B — Connecting Revision Tracking to the Tutor

The revision update was initially connected directly to each Tutor
interaction.

The resulting flow was:

    Student question
          ↓
    Tutor response
          ↓
    Update last_revised

This successfully demonstrated that a tutoring interaction could modify
persistent learning state in SQLite.

However, this approach was considered too granular.

Every question does not necessarily represent meaningful revision.

---

# 15C — Recording Revision at Session End

The revision update was therefore moved to the end of the tutoring
session.

The new flow is:

    Start tutoring session
          ↓
    Multiple questions and responses
          ↓
    Student exits
          ↓
    Update last_revised
          ↓
    Save to SQLite

The application uses:

    date.today().isoformat()

to record the current date.

For example:

    Last revised: 2026-08-21

The decision was made to interpret a completed tutoring session as
evidence that the student worked on the topic.

This is intentionally a simple first implementation.

We are not yet claiming that a tutoring session proves understanding or
mastery.

---

# 15D — Capturing Student Responses

The next step was to capture the student's responses from the current
conversation.

The Tutor already stores conversation messages in:

    self.messages

Each message contains a role such as:

    system
    user
    assistant

A new method was added to `Tutor`:

    get_student_responses()

The method examines the conversation history and extracts messages where:

    message["role"] == "user"

This provides the student's responses from the current session without
creating another persistent database table.

For example, a conversation might contain:

    You: What is integration?

    You: It is the reverse of differentiation.

    You: Why do we add C?

`get_student_responses()` can extract those student messages for later
analysis.

---

# Important Architectural Distinction

Lesson 15 established a useful separation between:

## Conversation Memory

Stored temporarily by the Tutor:

    self.messages

This contains the current tutoring interaction, including the student's
questions and responses.

## Persistent Learning State

Stored in SQLite:

    student_topics

This contains information that should survive between sessions:

    status
    confidence
    last_revised

The current architecture therefore separates:

    Conversation evidence
            ↓
    Temporary session memory

from:

    Learning state
            ↓
    Persistent database

This prevents the database from becoming a repository for every
conversation message.

---

# Important Design Decision

We deliberately did NOT allow Phi-4 to automatically change the
student's confidence based on its own assessment.

For example, we are not yet doing:

    Student answer
         ↓
    Phi-4 judges answer
         ↓
    Confidence = 70

There are several reasons for postponing this:

- A single answer may not provide enough evidence.
- LLM judgments of understanding can be unreliable.
- Confidence and demonstrated understanding are not necessarily the same
  thing.
- We want to establish reliable evidence collection before introducing
  automated learning-state changes.

# Emerging Feedback Loop

Cardinal now has the beginnings of the following loop:

    Student
       ↓
    Tutoring session
       ↓
    Student responses
       ↓
    Evidence available for analysis
       ↓
    Persistent learning state
       ↺

At present, only the activity portion of this loop is automated.

A session updates:

    last_revised

while:

    status
    confidence

remain unchanged.

# Lesson 15 Outcome

Cardinal can now:

- update a topic's `last_revised` date
- record revision at the end of a tutoring session
- preserve status and confidence while updating revision information
- retrieve student responses from the current Tutor conversation
- keep conversation memory separate from persistent learning state
- provide the foundation for future evidence-based adaptation

The next stage is to determine how Cardinal can use the student's
responses as evidence of understanding without relying on an overly
simplistic or unreliable automatic confidence score.
